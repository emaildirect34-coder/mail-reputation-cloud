# Email Direct ↔ Codex — contrat technique

Codex owns server-side code (VPS). Email Direct (this app) owns the dashboard, database and generated config. They communicate only through the HTTP contracts below.

## 1. KumoMTA on each sending server

The Lua config is generated by the app (`src/lib/kumo.server.ts`) from servers, IPs, VMTA pools, warmup plans and domain bindings. Codex must not hand-edit it: change data in the dashboard, the agent pulls the new version.

1. In the dashboard: Serveurs → server → « Installer l'agent ». This issues a one-time bearer token `kag_…` (stored hashed).
2. On a fresh Ubuntu/Debian VPS:
   ```bash
   curl -fsSL https://<app>/api/public/agent/install.sh | sudo AGENT_TOKEN=kag_xxx bash
   ```
   Installs KumoMTA, python3/zstandard, systemd `kumo-agent` and `kumo-events`.

Agent API (header `Authorization: Bearer kag_…`):

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/public/agent/config` | `{ lua, hash, dkim:[{domain,selector,key,bindingId}] }` — write `lua` to `/opt/kumomta/etc/policy/init.lua`, keys to `/opt/kumomta/etc/dkim/<domain>/<selector>.key`, reload when `hash` changes |
| POST | `/api/public/agent/report` | `{ version, config_hash, installed_bindings:[id], metrics:{cpu,ram,queue} }` — confirms DKIM installation |
| GET | `/api/public/agent/jobs?limit=N` | claim queued messages (RFC 5322 rendered) → inject into local KumoMTA HTTP `:8000/api/inject/v1` |
| POST | `/api/public/agent/jobs` | `{ results:[{id, ok, error?}] }` — injection acceptance |
| POST | `/api/public/agent/events` | ≤500 KumoMTA log records (Delivery/Bounce/TransientFailure/Feedback); deduplicated server-side; advance local cursor only after 2xx |
| POST | `/api/public/unsub/<token>` | Authenticated mailto unsubscribe from the sending server, with an empty body. A 404 means the token is unknown to that server. |
| GET | `/api/public/agent/campaign-control` | `{ holds:[campaignId] }` for this sending server. The agent mirrors these to campaign-scoped suspensions on its local KumoMTA admin API. |
| POST | `/api/public/agent/campaign-control` | `{ action:"permit", id:messageId }` rechecks eligibility just before injection. `{ action:"release", ids:[campaignId] }` explicitly authorizes removal of the agent's own holds. |
| POST | `/api/public/agent/campaign-control` | `{ action:"confirm-suppressions", ids:[messageId] }` confirms up to 200 Bloom candidates against the exact suppression table and returns `{ excluded:[messageId] }`. |
| GET | `/api/public/agent/suppression-snapshot` | Returns the signed binary from private app storage for authenticated agents. A superadmin can publish a new binary from the suppression dashboard. |

`GET /api/public/agent/config` includes `maintenanceSince` (timestamp or `null`) outside the configuration hash. When present, an updated agent checks local KumoMTA liveness, reads the `message_count` gauge from `http://127.0.0.1:8000/metrics.json`, and sends `maintenance: { since, messages }` in `/api/public/agent/report`. It echoes the supplied timestamp and omits the sample if the local check or metric is unavailable. The campaign claim endpoint keeps returning the usual `{ jobs: [] }` during maintenance, including for older agents. [KumoMTA metrics API](https://docs.kumomta.com/reference/http/kumod/metrics.json_get/)

Agents supporting scheduled campaign approval report `metrics.campaignApproval: true`. A scheduled job carries `approvalRevision` in the claim response. The agent echoes it when requesting the injection permit. A denied permit must leave the message uninjected. The application verifies the claim and the approved revision together; an agent without this capability receives no protected scheduled jobs.

Codex tasks: hardening (firewall, fail2ban, TLS certs for MTA-STS/DANE), TCP BBR, Ansible/cloud-init for N servers, load tests. Any Lua behaviour change is requested to Lovable so it lands in the generator.

Use `ops/smtp-network-audit.sh` on the VPS and inside the sender's network namespace to compare effective TCP settings and congestion counters. For a containerized sender with a separate network namespace, persist `net.ipv4.tcp_congestion_control: bbr` under the sender's Compose `sysctls` after checking host support. Evaluate listen-backlog drops and ephemeral port usage under representative load before changing socket limits. Avoid changing global TIME_WAIT reuse based on a single snapshot.

VMTA routing requires migration 0024, the current app policy and an updated agent with KumoMTA 2026.09.29 or newer. `jobs` may include `campaignId` and `vmtaPoolId`. The agent puts them in the HTTP recipient's private metadata as `campaign_id` and `pool_id`; the policy maps them to KumoMTA campaign and pool routing without adding message headers. Bulk campaigns can select active marketing pools only. An explicit pool waits for acknowledged inventory and an eligible IPv4 on that server, with no default-pool fallback. The default pool uses unassigned or active marketing IPv4s. Transactional, warm-up, paused and quarantined IPs cannot join that default path. After migration 0024, claims wait for a compatible agent to acknowledge the current policy, including campaigns on the default path. Plan the app, migrations and agent rollout together.

Campaign hold synchronization requires migration 0026, the updated policy generator and the updated agent. The agent processes delivery logs before it pulls work, refreshes signals every 20 jobs and rechecks every claimed job. On control errors it stops submitting new messages. A hold affects messages labeled with their campaign UUID on injection; SMTP transactions already in progress may finish. The VPS retains its own holds if the app is temporarily unavailable and never cancels an operator's manual suspension.

Apply migration 0028 and update the VPS event reporters before releasing the new unsubscribe endpoint. Route mailto unsubscriptions to the originating sending server. Browser GET requests only open the unsubscribe confirmation page. Mail clients can still send the RFC 8058 `List-Unsubscribe=One-Click` form POST directly. Sponsor conversions use the ID issued on an activated navigation or explicit click confirmation. Existing ledger transactions can still receive corrections with their original click IDs. Ordinary links continue to redirect if the request provides no interaction signal. An open pixel fetch remains an estimate, since email proxies can fetch it automatically.

Apply migration 0029 before enabling preference-center links in production. Recipients can choose their normal frequency or a maximum of one campaign injection per rolling seven days at `/preferences/<unsubscribe token>`. The cadence is shared across campaigns and sending servers. The permit API checks it just before injection, including previous sends. Messages already accepted by the sender may still arrive. An unsubscribe remains a separate permanent suppression and preferences cannot clear it. For branded links, forward `/preferences/*` and `/api/public/unsub/*` through the tracking proxy, then set `BRANDED_PREFERENCES_ENABLED=true` in the app. The default link uses the application host.

Migration 0031 adds recipient topic preferences. The campaign builder has an optional topic. The injection permit skips a tagged campaign if the recipient chose other topics, while untagged campaigns still follow the recipient's cadence. An older agent must be upgraded to use the permit endpoint before topic preferences or weekly cadence can take effect.

Migration 0032 adds voluntary 30- or 60-day pauses. The permit skips any campaign message due during the pause. It does not collect a backlog for the end of the pause. Lifting or expiring the pause keeps all other preferences, and a permanent unsubscribe always takes precedence. Messages already accepted by the MTA may still arrive.

Migration 0033 prepares the audience with cursor pagination and an exact suppression lookup inside PostgreSQL. It also adds the optional 365-day engagement window. The campaign builder excludes likely domain typos and requires acknowledgment when at least three valid-format addresses are affected and their share reaches 2%. No contact address is rewritten. The SMTP permit still rechecks the exact suppression list immediately before injection.

Migration 0034 attributes new terminal delivery records to the reporting agent's inventoried source IPv4. Update the app and event reporters after applying it. The shaping page shows the matrix in observation mode. Set `KUMO_ISP_SOURCE_ROUTING=true` to enable weighted routing inside the original marketing pool. The matrix uses terminal SMTP results from the previous seven days excluding the latest 24 hours. Each source in a pool needs 100 observations for that provider. A gap of at least two percentage points gives the better sources weight two and the others weight one. The matrix does not use transient deferrals, does not add sources or cross pools, and leaves warmup, existing throttles and campaign holds in force.

Migration 0035 adds the optional weekly digest format. An operator assembles multiple editorial sections and may schedule the issue in the campaign builder. Test Inbox uses the rendered digest. Only recipients who explicitly choose the digest receive it, and those recipients are excluded from ordinary campaigns. The permit rechecks the selected format, pause, topic and permanent suppression before injection. The same seven-day interval applies across servers. This feature does not gather past campaigns or create issues on its own.

Outbound DANE is opt-in with `KUMO_ENABLE_DANE=true`. It requires KumoMTA 2026.09.22 or newer and uses the validating Hickory resolver. The default upstream is `1.1.1.1:53`; set `KUMO_DNSSEC_RESOLVER` to your DNSSEC-capable upstream if different. Verify DNS resolution over UDP/TCP and test destination TLS policy on each sending server before enabling. The Orange/Wanadoo, Free and SFR/Neuf profiles serialize SMTP commands and cap a transaction at one recipient. Their rate throttle works at the message level.

`KUMO_REQUIRE_MODERN_TLS=true` makes outbound STARTTLS mandatory with certificate validation, TLS 1.2/1.3 and modern forward-secret OpenSSL suites. KumoMTA will defer or fail delivery to destinations that do not support the selected policy. The SMTP listener on port 25 keeps its independent configuration. Test representative destinations before enabling the option on the production application.

`KUMO_TLS13_ONLY=true` also disables TLS 1.2 for outbound SMTP. For receivers that request a client certificate, `KUMO_SMTP_CLIENT_CERT=true` configures KumoMTA to load `/opt/kumomta/etc/tls/smtp-client-chain.pem` and `/opt/kumomta/etc/tls/smtp-client-key.pem`. Install a certificate suitable for client authentication and its matching private key on every affected VPS before enabling this option. Keep the key readable only by the service. Client certificate support requires KumoMTA 2025.10.06 or newer. [KumoMTA TLS certificate](https://docs.kumomta.com/reference/kumo/make_egress_path/tls_certificate/)

For inbound DANE, the Lab reads the public MX and TLSA records and shows their DNSSEC validation status. It computes a `3 1 1` TLSA candidate from the public SMTP certificate's SubjectPublicKeyInfo in the browser. Use the certificate actually presented by every live address behind the MX on port 25, not the Caddy HTTPS certificate. Coordinate certificate and TLSA changes, publish both associations during a key rollover, and allow the DNS cache to expire before removing the old association. DNSSEC activation alone does not publish a TLSA record or change SMTP TLS settings.

On a host with Python 3, OpenSSL and outbound TCP port 25, run `python3 ops/verify-smtp-tlsa.py example.com mail.example.com <approved-sha256>` to check the key against every public address of the authenticated MX. The superadmin can then confirm the check and publish the first TLSA from the Lab. The application resolves the zone through the connected Cloudflare accounts, checks the configured sending IPv4 against the public DNSSEC-authenticated MX address and requires Cloudflare DNSSEC to be active. A different existing TLSA requires a coordinated key rollover. After publication, verify the authenticated record in the Lab.

For scheduled initial publication, add a target to the application's server-only `DANE_AUTOMATION_TARGETS` JSON array, with `domain`, `mx`, `fingerprint`, `serverId` and `approvedBy` (the UUID of a current superadmin). Schedule the verifier with the same pinned values and `--app-origin https://<app>`. Give that service `KAG_TOKEN` via `EnvironmentFile=/etc/kumo-agent/env` on its assigned VPS. After the live STARTTLS probes match, the agent submits to `POST /api/public/agent/dane-publication`. An empty target list disables publication. The endpoint only accepts exact configured targets from their assigned agents and rechecks the approver's current role. It reuses the manual DNS guard and never removes or rotates a record. Keep the timer separate from the delivery loop.

For systemd, install `ops/verify-smtp-tlsa.py` at `/usr/local/lib/email-direct/verify-smtp-tlsa.py` and the `ops/email-direct-dane@.service` and `ops/email-direct-dane@.timer` templates in `/etc/systemd/system/`. Set `DANE_DOMAIN`, `DANE_MX`, `DANE_FINGERPRINT` and `DANE_APP_ORIGIN` in `/etc/kumo-agent/dane-<label>.env` and enable `email-direct-dane@<label>.timer`. The service checks hourly with a randomized delay. It may be disabled after the initial record is publicly visible.

Apply migrations 0036 and 0037 before activating Bloom. `ops/suppression-bloom.py` builds a snapshot with `build <output> --capacity <N>` from an authorized list of suppression MD5 hashes on standard input. The builder, application and readers use the same 32-byte hexadecimal `SUPPRESSION_BLOOM_KEY` secret. A superadmin uploads only the signed binary from **Listes & suppressions**. The private bucket has no browser read policy. The app distributes the binary through the authenticated agent endpoint. The bitset expires after 24 hours. The exact database remains authoritative for positive and negative matches, even when the snapshot is unavailable. The tool does not export the suppression table or rebuild the snapshot on a schedule.

Install `ops/suppression-bloom.py` at `/usr/local/lib/email-direct/suppression-bloom.py` and install the `ops/email-direct-bloom.service` and `ops/email-direct-bloom.timer` files in `/etc/systemd/system/`. Configure `/etc/kumo-agent/suppression-bloom.env` with mode 0600 and set `SUPPRESSION_BLOOM_KEY`, `SUPPRESSION_BLOOM_FETCH_TOKEN` (the assigned Kumo agent token), `SUPPRESSION_BLOOM_URL=https://<app>/api/public/agent/suppression-snapshot` and `SUPPRESSION_BLOOM_SNAPSHOT=/var/lib/email-direct/suppressions.bloom`. Enable the timer and reinstall the current agent so its service reads the same environment file. The refreshed file is installed atomically. Before per-message permits, the agent submits only IDs of possible matches for exact batch confirmation. Failed downloads, expired snapshots and confirmation errors fall back to the normal per-message permit.

Transient SMTP retries use KumoMTA's native jittered exponential backoff with a 20-minute base interval. SMTP PIPELINING is negotiated with the remote host when enabled. Set `KUMO_SMTP_LOCKSTEP_SITES` in the app to a comma-separated list of exact KumoMTA site identifiers to require sequential commands for known incompatible MX clusters. The existing provider-specific sequential profiles remain in effect. The override applies when KumoMTA evaluates an egress path, and KumoMTA continues to manage transaction retries.

Google SMTP paths have a shared local limit of at most 10 simultaneous connections per source, plus a per-source/site connection-start throttle of 30 per minute with a burst of three. Each connection attempts at most 20 messages. Existing warm-up or health constraints can lower the path concurrency further.

The generated policy also shares a local connection limit and message throttle by source across explicitly listed aliases for Orange, SFR, Free and Microsoft. These groups are conservative policy labels. The original recipient domain and its normal DNS MX lookup remain in use. Orange, Free and SFR share 3 connections and 2 messages per second per source per group; Microsoft shares 10 and 5 respectively. Local egress path limits still apply.

To enable signed SMTP Return-Paths, publish the application with support for `dsn` events, update all VPS event reporters, then set a server-only `BOUNCE_HMAC_KEY` of at least 32 characters in the application. New Return-Paths include a compact message ID, timestamp and truncated HMAC. The application rejects external FBL complaints with missing or invalid signatures after activation, including feedback for older unsigned mail. Direct SMTP delivery, rejection and deferral records from authenticated agents remain supported.

For asynchronous bounces, the reporter forwards KumoMTA's parsed `OOB` logs as `type: "dsn"` with the inbound envelope destination in `returnPath`, the failed address and enhanced status in `dsn: { recipient, status }`, and the SMTP diagnostic in `smtpCode`. The application accepts only permanent failures with a valid signed Return-Path and a recipient matching the queued message on the authenticated server. It discards invalid reports and passes valid ones to the same deduplicated ingestion RPC as synchronous bounces. This requires the Return-Path domain's MX to route reports to the original sending agent. No raw DSN body or signature is stored with the resulting event.

## 2. Mail-Tester VPS (built by Codex)

Inbound SMTP sink on a dedicated domain (e.g. `check.example.com`, wildcard MX), analysis with Rspamd/SpamAssassin, DKIM/SPF/DMARC/ARC verification, RBL lookups (Spamhaus DQS), MIME/link checks. Exposes HTTPS JSON with `Authorization: Bearer <MAILTESTER_KEY>`.

`POST /api/v1/tests` → `201 { "test_id": "abc123", "email": "abc123@check.example.com" }`

`GET /api/v1/tests/:test_id` →
```json
{ "status": "waiting" | "done",
  "score": 9.4,
  "checks": {
    "spf":   { "pass": true,  "detail": "pass ip=1.2.3.4" },
    "dkim":  { "pass": true,  "detail": "2 signatures valid (s1,s2)" },
    "dmarc": { "pass": true,  "detail": "p=reject aligned" },
    "arc":   { "pass": true }, "rdns": { "pass": true }, "rbl": { "pass": false, "detail": "listed: ..." },
    "list_unsubscribe": { "pass": true }, "mime": { "pass": true }, "links": { "pass": true } },
  "penalties": [ { "rule": "HTML_IMAGE_ONLY_16", "points": -0.6, "description": "..." } ],
  "headers": "raw received headers" }
```
`test_id` matches `^[A-Za-z0-9_-]{4,64}$`. Results kept ≥ 7 days.

Once deployed, the owner stores `MAILTESTER_URL` and `MAILTESTER_KEY` as app secrets; the Lab page « Testeur 10/10 » works with no code change.

## Mail-Tester v2 — structured checks
Request `GET /api/v1/tests/:id?version=2` for `checks[]` (each `{id,status:pass|warn|fail,points,detail,fix}`). The unversioned endpoint keeps the original dictionary for deployed clients. `spam_score` reports the highest available raw score. The final grade applies a spam-engine penalty only once.
- `rspamd` + `spamassassin` dual engine scores (both returned, worst one penalizes).
- `rfc8058` List-Unsubscribe-Post: List-Unsubscribe=One-Click present and DKIM-signed.
- `dmarc_alignment` strict (adkim=s/aspf=s) result, `arc` chain validity.
- `mta_sts`, `dane_tlsa`, `bimi_vmc` for the From domain.
- `subnet24` samples the five nearest IPv4 neighbors using IP DNSBLs whose positive controls pass. The result states coverage and lists hits.
- `fr_isp` hints for Orange/SFR/Free/Laposte (rate, HELO, rDNS forward-confirmed).
- `gmail_yahoo_2024` compliance summary.
Failing checks provide a `fix` string. DNS or header fixes include the required values when the test has enough information. Infrastructure and reputation findings provide the operational remediation.

## 3. Contacts Vault VPS (149 GB customer base, deferred)

The dashboard never stores the full base. A dedicated VPS (ClickHouse recommended, ~2 TB NVMe) holds contacts; the site drives it over HTTPS with `Authorization: Bearer $VAULT_KEY`. Secrets on the site: `VAULT_URL`, `VAULT_KEY`.

Contact columns: `email` (lowercase), `email_md5`, `domain`, `isp` (gmail|outlook|yahoo|orange|sfr|free|laposte|other), `country`, `first_name`, `created_at`, `last_open_at`, `last_click_at`, `status` (active|invalid|suppressed|bounced|complained), `tags` (array).

- `GET /api/v1/stats` → `{ "total": n, "active": n, "invalid": n, "suppressed": n, "by_isp": {"gmail": n,...}, "by_country": {"FR": n,...}, "disk_bytes": n }`
- `POST /api/v1/imports` body `{ "source_url": "https://... or sftp path", "format": "csv", "delimiter": ",", "mapping": {"email": 0, "first_name": 1, "country": 2} }` → `{ "import_id": "..." }`. Streams the file, dedupes by `email_md5`, validates syntax/MX, applies suppression.
- `GET /api/v1/imports` → `{ "imports": [{ "import_id", "status": "queued|running|done|failed", "rows_read", "rows_inserted", "rows_rejected", "started_at", "finished_at", "error" }] }`
- `POST /api/v1/segments/count` body `{ "filters": { "isp": ["gmail"], "country": ["FR"], "active_days": 90, "tags": [], "status": "active" } }` → `{ "count": n }` (must answer < 2 s, use materialized aggregates).
- `POST /api/v1/segments/export` body `{ "filters": {...}, "campaign_id": "uuid", "limit": n, "callback_url": "https://mail-reputation-cloud.lovable.app/api/public/vault/batch" }` → `{ "export_id": "..." }`. The VPS must exclude MD5 suppressions fetched from the site and push recipients to the campaign queue in batches of 5 000 (contract for the callback to be finalized together).
- `POST /api/v1/suppressions` body `{ "md5": ["..."] }` → marks contacts suppressed (site calls this on every new unsubscribe/complaint).

## 4. Inbox placement tester (add to the Mail-Tester VPS)

Goal: show where a real email lands (Inbox / Promotions / Spam) at each big mailbox provider.

The placement implementation is deployed as a Mail-Tester Compose overlay in `mail-tester/`. Superadmins manage dedicated Gmail seed accounts in Settings. The authenticated `/api/v1/placement/seeds` API checks IMAP login before saving the app password, encrypts it in SQLite using `PLACEMENT_KEY` from the VPS-only `.env.placement`, and returns addresses only. The worker opens folders read-only and leaves received messages in the seed mailbox.

Additional TLS IMAP accounts can be configured in `/etc/mailtester/seeds.yml` on the VPS. This file is mounted read-only and must be restricted to the service administrator. Each entry requires `provider`, `address`, `host` and `password`. Optional fields are `port` (default `993`), `username`, `spam_folder` and `other_folder`. The worker can report Outlook Other when it is exposed as a distinct IMAP folder. Providers that require OAuth or a local bridge need separate setup.

Seed mailboxes: real accounts owned by us (Gmail ×2, Google Workspace, Outlook.com, Yahoo, AOL, GMX, Orange, Free, SFR, La Poste, Proton via Bridge, iCloud…). Their IMAP credentials (app passwords) live only on the VPS (`/etc/mailtester/seeds.yml`), never in the dashboard.

Same Bearer key as §2.

- `POST /api/v1/placement` → `201 { id, token, expires_at, seeds:[{provider,address,placement:"pending"}] }`
  `token` is a short random string (e.g. `ED-7F3K9Q`). The user must put it in the Subject or body of the test email and send it to every seed address.
- `GET /api/v1/placement/:id` → `200 { id, token, status:"waiting"|"done", seeds:[{provider,address,placement,folder,received_at}] }`
  `placement`: `inbox` | `promotions` (Gmail category tab via `X-GM-LABELS` `\\Category\\Promotions`, or Outlook "Other"/Focused) | `spam` (Junk/Spam/Bulk/Courrier indésirable) | `pending` | `missing` (not found after 15 min).
  Poll each seed's INBOX + Spam folder over IMAP about every 20 s, search by token, and record the folder without modifying the message. `status:"done"` once every seed is not `pending`.
- Keep results 7 days. Unknown id → 404.

## 6. Incident notifications

After applying migration 0020, schedule an authenticated POST to `/api/public/jobs/incident-notifications` once per minute using the same cron authentication as the daily report. It checks new IP quarantines, FBL complaint rates above 0.3%, and agents with no heartbeat for five minutes. Notifications are recorded per channel to avoid resending resolved delivery attempts.

After migration 0062, the same periodic call also marks up to 5,000 messages whose campaign deadline has passed and whose injection permit was never granted. The authenticated agent claim and permit endpoints enforce the same deadline without changing the agent request format.

After migration 0065, the periodic call also refreshes the cockpit incident center. It records campaign blocks, unresolved injection receipts and unavailable sending agents. It records signal recovery separately from an operator’s resolution. A signal that returns after recovery creates a new incident.

Migration 0066 enforces sender-domain daily quotas through the existing claim and permit contracts. The final permit reserves one slot across all agents for the exact From domain and UTC day. If another agent takes the last slot first, the pending message returns to the application queue and the permit response is denied.

After applying migration 0022, set `CADDY_HEALTHCHECK_URL` to the public HTTPS probe and `CADDY_HEALTHCHECK_STATUS` to its expected status (defaults to `200`). ## 7. Message trace

List-backed campaigns use `List-Id` with the list UUID under the app hostname or `LIST_ID_DOMAIN` if configured. Keep this namespace stable between deployments. Optional `LIST_HELP_URL` and `LIST_OWNER_EMAIL` add genuine support contacts. Set `LIST_ARCHIVE_URL` only if it points to an existing reader-facing archive. These settings apply across the private deployment. Test messages without a list keep their existing headers.

The delivery log can look up a queue UUID or a full Message-ID. Migration 0038 adds an index for that lookup. The trace displays the stored campaign subject and variant, queue timestamps, and up to 100 recent SMTP events. An IP is shown only when attributed by the reporting agent. A worker with log access can follow existing log entries. The superadmin can also inspect messages that have no SMTP events yet.

The message trace classifies explicit SMTP diagnostics and keeps the original response alongside them. Ambiguous or conflicting signals stay unclassified. The agent copies valid enhanced codes into the diagnostic text for display. These labels do not change the existing retry or suppression rules.

## 8. Campaign recipient checks

Migration 0041 adds confirmation proofs for opt-in links. Set `SUBSCRIPTION_CONFIRMATION_KEY` to a random 32-byte hexadecimal secret in the application.
